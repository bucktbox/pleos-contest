**3. 법·정책 리스크**

다음은 위법 확정이 아니라 **현재 명세로 판단할 수 없거나, 상용화 전에 충족해야 할 조건**입니다.

**① 위치정보 — 높음**

- 목적지 설정값은 미래의 의도일 수 있어 현재 위치와 항상 같지는 않습니다. 반면 **사용자와 연결된 매장 도착 시각·방문 장소 ID**는 실제 위치를 드러낼 수 있습니다.
- 좌표를 보내지 않고 `userId + sponsorStoreId + arrivalTime`만 전송해도 위치정보·개인정보 검토가 끝나는 것은 아닙니다.
- 서버 매칭, 도착 과금, 개인별 목적지 랭킹을 하려면 어떤 장소 정보를 언제 서버로 보내는지 명확해야 합니다.
- 스폰서에게 개인별 방문 기록을 제공한다면 수령자·목적·항목·보유기간·동의와 제공 통보 체계를 검토해야 합니다. 위치정보법 제19조는 제3자 제공 동의와 통보를 규정하고, 동의를 받은 경우의 모아 통보 규정도 두고 있습니다.
- 위치기반서비스사업 신고·개인위치정보사업 등록 중 무엇이 적용되는지는 **직접 수집·이용·제공 역할과 예외에 따라 판단**해야 합니다. “소규모니까 면제”, “좌표가 없으니 무관”으로 처리할 수 없습니다. [위치정보법](https://law.go.kr/LSW/lsInfoP.do?lsId=009882)

**제출 전 조치:** 데이터 흐름도를 작성하고, 최소한 1차 범위에서는 목적지·도착의 기기 내 처리와 외부 미전송 여부를 명시하십시오. 스폰서 제공은 계약·동의 구조가 정해질 때까지 확장 계획으로 내려야 합니다.

**② 포인트·쿠폰 — 높음**

- 여러 사업자의 재화·서비스에 사용하는 전자적 가치라면 선불전자지급수단 해당 여부를 검토해야 합니다.
- **무료 지급·현금 인출 불가라는 이유만으로 자동 제외되지 않습니다.**
- 매장 자체 할인권, 특정 상품 교환권, 여러 가맹점에서 쓰는 잔액형 포인트는 구조가 다릅니다. 각각 발행 주체·사용처·재원·환급·소멸·정산을 정해야 합니다.
- 선불업 등록 면제 여부와 충전금 보호 등 적용 의무도 구분해야 합니다. 금융위는 2024년 제도 개편에서 모바일상품권 등을 포함한 보호 범위 확대를 안내했습니다. [금융위원회 설명](https://www.fsc.go.kr/po010102/83004?curPage=131&srchBeginDt=&srchCtgry=&srchEndDt=&srchKey=&srchText=)

**제출 전 조치:** 통합 포인트 지갑 구현 약속을 빼고, 가상 보상으로 시연하십시오. 상용 실험은 계약된 매장의 할인 혜택 또는 적격 발행사 연계를 검토하는 편이 현실적입니다.

**③ 개인정보 — 높음**

닉네임·기기 식별자·운전 결과·목적지·쿠폰 사용을 결합하면 이름이 없어도 개인을 식별하거나 연결할 수 있습니다. 필요한 것은 다음입니다.

- 처리 목적과 적법 근거, 최소 수집 항목, 보유·삭제 기간
- 공개 랭킹의 표시 범위와 참여 선택
- 스폰서 제공과 서버 운영 위탁의 구분
- 클라우드·분석 도구의 국외 이전 여부
- 공유 차량에서 운전자 구분과 타인의 기록 노출 방지

운전·방문 기록을 법정 민감정보라고 일괄 단정할 수는 없지만, 방문 장소에 따라 민감한 사생활이 추론될 수 있습니다. [개인정보 보호법](https://law.go.kr/법령/개인정보보호법)

**④ DO — 높음, 서비스 성립 조건**

공식 지침은 단순히 터치를 잠그라는 수준이 아닙니다. 앱 분류·운전 상태·지역별 제한을 적용하고, 게임 등 주의 분산 활동을 유도하지 않도록 요구합니다. 따라서 HP·봉인 게이지·콤보 효과음이 있는 현재 설계를 “100% 방어”라고 할 수 없습니다. **‘수동 수집만 주행 중 허용되는가’와 ‘실시간 게임 피드백도 허용되는가’를 구분해서 확인해야 합니다.** [운전 안전 설계 지침](https://document.pleos.ai/en/docs/pleos-only/vehicle-app-planning-guide/driver-distraction-guideline), [DO 구현 가이드](https://document.pleos.ai/en/docs/pleos-only/vehicle-app-developer-guide/driving-restriction-development-guide)

**4. 기술 실현성·17일 개발 범위**

**① 1.5초 선행 판정: 이벤트 순서 시연은 가능, 안전 매너 판정은 미검증**

필요한 예외 처리가 빠져 있습니다.

- 깜빡이를 오래 켜둔 상태의 반복 득점
- 좌측 깜빡이와 우측 조향처럼 방향이 다른 경우
- 점멸 상태 변화를 매번 새로운 점등으로 인식하는 경우
- 커브·주차·유턴·긴급 회피·방향지시등 자동 해제
- 경계값 근처에서 콜백 지연 때문에 결과가 뒤집히는 경우

앱 수신 시각만 쓴다면 관측 시간차에는 두 신호의 전달 지연 차이가 섞입니다. 동일한 단조 증가 시계로 기록하더라도 **센서 발생 시각 정확도까지 확보되는 것은 아닙니다.**

검증은 정상 회전·커브·주차·긴급 회피 등 정답이 있는 시나리오를 두고 오탐·미탐과 지연을 측정해야 합니다. Console 슬라이더 시연은 이벤트 연결을 증명하며, 실도로 신뢰도는 증명하지 못합니다.

**② 조향각 변화율: 승차감·위험도를 직접 나타내지 않음**

같은 핸들 변화도 차속·조향비·차종에 따라 차량 거동이 다릅니다. 저속 주차의 큰 조향을 벌점 처리하거나, 고속에서 작은 조향의 위험을 놓칠 수 있습니다. 도로 곡률·회피 필요성도 없습니다.

따라서 “무결점 98점 드라이버”는 현재 센서와 검증으로 뒷받침되지 않습니다. **특히 현금성 보상과 공개 순위에 사용하기 어렵습니다.**

**③ 차속·제동: Soft Stop을 핵심 약속에서 제외할 것**

- 지정 목록에는 실제 차속 getter가 없습니다.
- v4.7의 브레이크 `Boolean` 표기는 개도율 제공 주장과 구분되어야 합니다. **이번 이름 목록과 공개 API 본문만으로는 반환형을 독립 재확정하지 못했습니다.** v4.5 역시 Boolean으로 기록합니다.
- Boolean이면 밟음·뗌과 빈도는 알 수 있지만 제동 압력·페달 깊이·차체 감속·저크는 알 수 없습니다.
- Console의 0~100% 슬라이더는 앱에 동일한 연속값이 전달된다는 증거가 아닙니다.
- FusedLocation 속도를 쓸 수 있더라도 저속·지하·터널의 품질, 갱신 주기, 오차와 결측을 확인해야 합니다. 속도를 미분해 감속도를, 다시 미분해 저크를 얻을수록 오차에 민감합니다.
- 트립 거리 차분도 갱신 주기·해상도가 충분해야 합니다. Console의 총거리 1km 조작 지원이 트립 거리 기반 속도 검증을 보장하지 않습니다.

**“브레이크를 나누어 밟으면 보상”은 삭제를 권고합니다.** 도로 상황에 필요한 제동을 미루거나 불필요하게 조작할 유인이 생길 수 있다는 기술·안전상 우려입니다. 긴급제동을 화물 파손·실물 보상 상실로 연결하는 규칙도 재설계해야 합니다.

**④ 서버 범위와 WBS: 명백히 불일치**

[현재 WBS](docs/report/pleos_v4_7.md:217)에는 Mock JSON 정의와 화면 바인딩이 있지만, 다음 작업은 없습니다.

**5. MAU·리텐션·수익성 수치**

**현재 숫자는 전망이라기보다 근거 없는 목표치입니다.**

| 수치 | 문제 |
|---|---|
| 초기 50만 대 × 설치율 40% × 월 활성률 75% = MAU 15만 | 산술은 맞습니다. 세 입력의 근거와 사용자 정의가 없습니다. 차량 1대와 사용자 1명이 같다는 보장도 없습니다. |
| 2028년 300만 대 → MAU 180만 | 초기에는 보급 차량의 30%가 MAU인데 이후에는 **60%**로 상승합니다. 설치·활성 전환율 개선 설명이 없습니다. |
| W1 72%·W4 55% | 실험·비교 코호트·보상 비용·지표 정의가 없습니다. 단일 주차 재방문인지 해당 주 내 재방문인지도 불명확합니다. |
| DAU/MAU 60% | MAU 15만이면 일 활성 9만 명입니다. 30일 기준 평균 약 18일의 활동이 필요합니다. 주말 사용자까지 포함한 구성에서 이를 지지할 근거가 없습니다. |
| 자동 실행을 통한 리텐션 | 수집 서비스 실행과 사용자의 자발적 재방문을 혼동합니다. 보상 화면 확인·결과 열람 등 의미 있는 행동을 별도 정의해야 합니다. |

권장 MAU 산식은 다음입니다.

> **대상 지역의 호환 차량 수 × 사용자 환산 계수 × 앱 도달률 × 설치율 × 권한 동의율 × 월 의미 행동률**

보수·기준·낙관 시나리오를 제시하되, 각 입력을 **외부 근거 / 실측 / 미검증 가정**으로 표시하십시오. W4 리텐션은 17일 안에 새 사용자 코호트로 검증할 수 없으므로, 제출 시점의 실측값처럼 쓰면 안 됩니다.

보상 재원도 검토가 빠졌습니다. **추정 예시로**, 500P=500원, DAU 9만 명, 1일 1회 지급, 월 30일을 가정하면:

- 포인트 재원: **월 13.5억 원**
- 이것이 스폰서 예산의 70%라면 필요 예산: **월 약 19.3억 원**
- 커피 쿠폰 원가·발행 수수료·부정 수령·운영비는 별도

이것은 비용 예측이 아니라 **현재 예시가 요구하는 자금 규모를 보여주는 조건부 계산**입니다. 할인권 액면가와 실제 원가, 포인트 지급 빈도도 구분해야 합니다.

“예산 70% 지급·30% 수수료”에서 30%는 순이익이 아닙니다. 또한 집·회사에 이미 갈 사람에게 주는 보상을 로컬 매장이 지속 후원할 이유가 약합니다. **일상 리텐션을 만드는 출퇴근 보상과, 스폰서가 돈을 낼 추가 방문 유도가 서로 맞지 않습니다.**

**6. v4.5 대비 되살린 요소의 타당성**

[개발자 측 v4.5 PART 6](docs/report/마스터리포트_v4.5.md:268)의 제한을 되돌릴 새 근거가 v4.7에 없습니다.

| 되살린 요소 | v4.5 판단 | v4.7 평가 |
|---|---|---|
| 개인 점수 TOP10 | 점수 비교·공개 개인 순위 제외 | **부적절.** 순정 중복·채점 공정성·조작·개인정보 문제가 재발. |
| 행정동 | 사용자가 직접 고른 동네의 공동 합계로 제한 | **설계 미정.** v4.7은 목적지 또는 행정동이라고만 해 자동 추론인지 수동 선택인지 불명확. 연속 GPS 점령이 완전히 부활했다고 단정할 수는 없음. |
| 보험사 UBI 스폰서 | 기존 순정·보험 제휴와 중복해 제외 | **현재 근거로 복원 불가.** 캠페인 후원과 보험료 산정 연계를 구분해야 함. |
| 주행 중 FusedLocation 속도 | 위치 처리 최소화, 거리 기반 추정 우선 | **조건부 가능.** 연속 위치 취득과 기록·전송은 다른 개념이므로 기술적으로 곧바로 금지는 아님. 다만 정확도·권한·데이터 처리 검증 없이 복원됨. |
| 1.5초 고정값·차선 변경 | 임계값 미확정, 차선 변경 판정 제외 | **퇴행.** 검증 전 숫자와 판정 범위를 확정 표현으로 바꿈. |
| 고정 리텐션 목표 | 근거 확보 후 기재 | **부적절.** 근거 없이 더 정밀한 숫자로 복원. |
| 서버 | 최소 기능·작업 일정·실패 시 축소 기준 명시 | **후퇴.** 제품 약속은 커지고 서버 일정·축소 기준은 사라짐. |

v4.5도 완성된 기술 정본은 아닙니다. “페달을 급하게 깊이 밟음” 서술은 Boolean 전제와 충돌하고, Console에서 임계값을 조정해도 실차 타당성 검증은 별도입니다. 서버 합산 역시 조작 검증을 대신하지 못합니다.

**7. 내부 모순**

1. **“단일 코어 루프” ↔ 다수의 사업 시스템**

   1.1에서는 확장 논리라면서 ③·사용 시나리오에서는 즉시 통합 포인트와 쿠폰을 줍니다.

3. **“Zero-UI·시선 분산 원천 방지” ↔ HP·충전 게이지·금 가는 소리·콤보 이펙트**  
   무조작이 무주의 분산을 뜻하지 않습니다.

4. **`Gear != P` ↔ D 전환만 설명**  
   R·N·기어 불명·콜백 지연의 처리와 플랫폼 제한 우선순위가 없습니다.

5. **“목적지 도착+P” ↔ 시연에서는 P 클릭만으로 개봉**  
   좌표·도착 이벤트 없이도 열리는지, 위치가 모의 입력인지 불명확합니다.

6. **“깜빡이를 안 켜면 상자가 깨져 안 열림” ↔ HP·등급별 보상**  
   단 한 번 실패 시 전부 상실인지, 부분 보상인지 기준이 충돌합니다.

7. **출퇴근 자동 카고 ↔ 깜빡이 열쇠가 필수**  
   조향 기회가 없는 정상 경로는 어떻게 해금하는지 없습니다. 불필요한 조작을 유도할 수 있습니다.

8. **벨트 100% 일치 버프 ↔ 착석만 켜는 시연**  
   지원 불명 좌석·카시트·후석 중앙석·미수신 상태의 처리도 없습니다.

9. **조명 원복 ↔ 색상만 백업**  
   밝기도 바꾸는데 표에는 밝기 조회·백업이 빠져 있습니다. 재출발·프로세스 종료·사용자 변경과 충돌할 때의 복원 정책도 없습니다.

10. **실제 랭킹·리워드 약속 ↔ Mock JSON 바인딩 일정**  
    시연 데이터와 실제 구현의 경계가 표시되지 않습니다.

**Top 1 — ‘차선 변경·안전 평가’를 ‘검증 범위가 제한된 이벤트 규칙’으로 수정**
